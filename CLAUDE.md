# Historia Twojego Domu — project brief for Claude Code

## What this project is
A one-page Polish-language website. A visitor types a Kraków street and a
building number. The site shows historical and architectural information
about that building, and notable places near it.

Goal (from the owner): as much information as possible for every Kraków
address. See `PLAN.md` for the phased plan and what is done.

Repo: https://github.com/glepeyko/krakow-building-history (branch `main`).

## Current state (after iteration 2, 2026-11-19)
- Static site: `index.html`, `assets/style.css`, `assets/script.js`.
  No backend. Preview locally with `python -m http.server 8000`
  (also in `.claude/launch.json` as "site").
- Data the site reads:
  - `data/streets.json` — 2,823 streets for the autocomplete:
    `{name, search, file, entries}`.
  - `data/streets/<file>.json` — one file per street, fetched when the
    visitor searches: `{name, search, story{}, districts{}, entries[],
    numbers{}, pois{}}`.
    - `story` ("O ulicy" block; facts only, the page writes the sentences):
      `{named_after: [{wikidata, label, description, years, wikipedia,
      person, via: ["wikidata"|"osm"]}], names: [{name, from, to}] (dated
      name history, Wikidata P1448), old_names: [..] (OSM old_name),
      wikidata, wikipedia (street article, linked not copied),
      districts: [district numbers the street runs through],
      municipalities: [neighbouring gminy, for streets that leave Kraków]}`.
    - `districts`: `{"<number>": "<name>"}` for the numbers used in this file.
    - `entries`: building records (schema below).
    - `numbers`: every known house number on the street (~71k in total)
      → `{lat, lon, osm, building, levels, start_date, architect, name,
      district (1–18) or municipality ("gmina Zielonki", for the ~3k
      addresses outside Kraków), entries: [entry ids], nearby: [[poi id,
      metres], ...]}`. A slot with `moved_to: "6"` marks a number the
      register gives wrongly (see corrections): the page shows what we know
      about that number and a "Zobacz … 6" link. No automatic redirect
      (owner decision, 2026-11-20).
      `nearby` = up to 6 places within 150 m; if none, up to 3 within 600 m.
    - `pois`: the notable places referenced by `nearby` in this file.
  - `data/research/ai_drafts.json` — AI-researched texts (committed, edited
    by hand/agents, not generated by the build): `{entry_id, address, text,
    sources: [{title, url}], wikipedia, status: "ai_draft_unverified" |
    "verified",
    researched_at, verification: {verdict, removed[], checked_urls[]}}`.
    Every sentence ends with citation markers `[1]`, `[1,2]` (1-based into
    `sources`); `tests/test_data.py` enforces this. The owner's review copy
    is a Claude doc "Opisy AI do sprawdzenia — iteracja 2"
    (https://claude.ai/artifact/PujNgMBMoB1S9aJiHntC9o); carry edits made
    there back into this file.
  - `data/research/corrections.json` — owner-approved fixes to register data
    (`{entry_id, field: "building_number", from, to, reason, decided_by,
    decided_at, sources[]}`), applied by build.py; the entry gets
    `correction{}` and the page shows the change with its sources.
- Data pipeline (Python 3.10+, `pip install -r requirements.txt`):
  1. `python scripts/sources/fetch_wikidata.py` → `source-data/raw/wikidata.json`
  2. `python scripts/sources/fetch_osm.py` → downloads the Małopolska extract
     (~220 MB; Geofabrik, falling back to the download.openstreetmap.fr
     mirror — Geofabrik drops connections from the cloud environment) and
     writes `osm_addresses.json`, `osm_notable.json`, `osm_streets.json`
     (street name:etymology / old_name / wikidata tags) and
     `osm_districts.json` (the 18 dzielnice, admin_level=9) and
     `osm_municipalities.json` (31 neighbouring gminy, admin_level=7). (The public
     Overpass API timed out for a whole-city query; do not go back to it for
     the bulk import.)
  3. `python scripts/sources/fetch_wikidata_streets.py` (after step 2) →
     `wikidata_streets.json`: Kraków street items (P138, P1448+P580/P582,
     pl.wikipedia article) and the people/places they are named after.
  4. `python scripts/sources/fetch_nid.py` → `nid_krakow.json`: Kraków rows
     of the NID register of immovable monuments (dane.gov.pl dataset 1130,
     CSV in Windows-1250; the URL is looked up via the dane.gov.pl API).
  5. `python scripts/sources/fetch_commons.py` (after step 1) →
     `commons_images.json`: 960 px thumbnail URL, author, licence and file
     page for every Commons photo our Wikidata items reference.
  6. `python scripts/build.py` → reads the GEZ Excel + raw files +
     `data/research/ai_drafts.json`, writes `data/` and `reports/coverage.md`.
  `source-data/raw/` is git-ignored; re-run steps 1–5 to refresh it. Each
  step degrades gracefully: build.py skips stories/districts/NID with a
  warning if a raw file is missing.
- The cloud environment `krakow-building-history` allows the hosts these
  fetchers and the research agents need (Wikidata, Wikipedia, OSM mirror,
  dane.gov.pl, zabytek.pl, muzeumkrakowa.pl, mnk.pl, visitmalopolska.pl …).
  It also allows dbc.wroc.pl (Chmiel, "Domy krakowskie" — public-domain
  DjVu with a text layer; `apt-get install djvulibre-bin` for `djvutxt`)
  and bazhum.muzhp.pl. sztetl.org.pl answers 403 and krakow.travel is
  unreachable from it.
- `scripts/lib/address.py` — the one place for address normalization and
  street matching. `scripts/lib/geo.py` — point-in-polygon district lookup.
  Tests: `python -m unittest discover tests`.
- `reports/coverage.md` — the scoreboard. Regenerated by every build;
  compare it in git to see what an iteration changed.

## Building record schema (entries)
Original GEZ fields — keep these names:
`id, street, street_search, building_number, address_raw, alt_address,
district_number, district_name, type_and_name, dating, author,
register_number, source, status`.
- `id`: the GEZ sheet reuses 52 ids; build.py renames later duplicates to
  `"<id>-2"` so ids are unique (the page looks entries up by id).
- `street` is now the canonical OSM street name (e.g. "aleja Juliusza
  Słowackiego"); the register's own spelling stays in `address_raw`.
- `building_number` is normalized ("1 a" → "1a", "14/16" → "14-16").
- `district_number/district_name` come from GEZ; when GEZ has none (all
  Wikidata-only entries) they come from the OSM boundaries and
  `district_source: "OpenStreetMap"` is set.
Optional fields (omitted when empty):
- iteration 1: `lat, lon, osm, wikidata, wikipedia, image (Commons file
  name), name (proper name, e.g. "Kamienica Pod Jaszczurką"), styles[],
  wd_description, author_wikidata (architect from Wikidata when GEZ has none)`.
- iteration 2, NID register: `nid_name` (official name), `nid_register`
  (register documents, e.g. "A-185 z 1931-06-25"), `nid_register_date`,
  `nid_chronology`, `nid_style` (skipped when "nieznany"/"inny"),
  `nid_url` (zabytek.pl record), `nid_inspire_id`.
- iteration 2, corrections: `correction {field, from, to, reason, sources}`.
- iteration 2, photos: `photo {thumb, width, height, author, license,
  license_url, page}` — only when author and licence are known.
- iteration 2, AI drafts: `ai_description`, `ai_sources [{title, url}]`,
  `ai_researched_at`. The page shows these only inside the block
  "Opis przygotowany przez AI — niezweryfikowany".
Entries that exist only in Wikidata have `id: "wd-Q…"` and
`source: "Wikidata"`.
`status`: `verified` = taken from a published source (GEZ, Wikidata), not
AI-written. `ai_draft_unverified` = the entry carries an AI-drafted text
(its GEZ/Wikidata fields are still register data). Planned: `not_researched`.
Approving an AI text: the owner approves it, then set its `status` to
`"verified"` in `ai_drafts.json` (add `approved_by`, `approved_at`) and
rebuild. The build then sets `ai_approved: true` and the page shows the text
as a normal description with its numbered sources and NO public AI label
(owner decision, 2026-11-20). Only the owner can approve; agents never
promote their own texts.

## Known limitations
- Building descriptions exist for ~9% of addresses (GEZ + Wikidata) plus 27
  AI-researched texts (all approved by the owner on 2026-11-20, shown
  without the AI label). Thanks to the 600 m fallback, ~95% of addresses show at least
  a nearby place; outer-district fallback places can be 400–600 m away.
- Street stories cover 550 of 2,823 streets (25% of addresses): only
  streets with a Wikidata item or OSM name:etymology/old_name tags. Dated
  name histories exist for only 5 streets (Wikidata rarely has P1448 with
  dates); former names from Wikipedia articles are not parsed yet. Patron
  birth/death years come from Wikidata and can be imprecise for early
  saints.
- 2,968 addresses (4%) lie outside Kraków: neighbouring gminy with Kraków
  postcodes (the OSM filter uses postcodes 30-/31-). Owner decision: keep
  them; the page names the gmina. Same-named streets in Kraków and in a
  neighbouring gmina (e.g. "Krakowska") share one street file. 19 GEZ
  records disagree with the OSM district (not checked).
- NID register: 1,113 entries linked. 166 NID rows have an address that is
  not in our entries (could become new entries), 89 are ambiguous at their
  address, 255 have neither an address nor a unique register number
  (ensembles, parks).
- Mykwa Wielka: GEZ says Szeroka 5; owner decided Szeroka 6 (as Wikipedia,
  VisitMalopolska, Wikidata). Fixed via corrections.json; no. 5 shows a link to no. 6.
- The same object can appear 2–3 times in "W pobliżu" when GEZ, Wikidata
  and OSM name it differently (e.g. Fort 48a Mistrzejowice).
- 223 GEZ records have no parsed building number (forts, viaducts, parks,
  areas); 214 GEZ streets did not match an OSM street. They are still listed
  when a visitor searches the street without a number.
- ~620 GEZ records have no coordinates (no OSM address match), so they get
  no "nearby" list.
- Wikidata ↔ GEZ links use register number, address, or position (≤20 m)
  plus a type-compatibility check. Position-based links can still be wrong
  in dense blocks; spot-check when changing `compatible()` in build.py.
  The AI pilot showed many famous buildings (e.g. Rynek Główny 10, 13, 33,
  43, 45) have a Wikipedia article that the Wikidata link did not reach.
- OSM `start_date` is rare (~200 buildings) and only taken from building
  outlines, not from shop/company points.
- AI drafts: the subagents' WebFetch tool did not see network changes made
  mid-session, so research and verification fetched pages with `curl`
  (owner approved). Wikipedia rate-limits parallel agents (HTTP 429): pace
  requests ~4 s apart. sztetl.org.pl still answers 403. The verifier is
  not perfect: the editor pass caught 3 slips it let through (a wrong
  "nearly four centuries", a date contradicting the next owner, an
  inferred name origin) — keep a human/editor read after verification.
- Photos (owner decision 2026-11-20, option 2): a medium Commons photo on
  the card (1,203 entries), always with "Fot. author, licence, Wikimedia
  Commons". Images load from Wikimedia's thumbnail host in the visitor's
  browser; the cloud environment cannot reach that host, so screenshots
  there show empty photo boxes. Authors are plain text from Commons
  metadata (truncated at 120 characters).
- Contact form still opens the visitor's mail program (`mailto:` to
  `CONTACT_EMAIL` = contact@krakowhleb.pl in `script.js`); no form service.

## Working conventions — please follow these
- Keep the site in Polish. Keep it text-focused (medium photos on cards
  are approved; every photo carries its author and licence). Keep it one page.
- Keep the diacritic-normalized, substring-match autocomplete. Do not
  replace it with an exact-match-only search.
- New building records must match the field names above. Open a file in
  `data/streets/` and check one record before you add new records.
- Every value from data files must go through `esc()` before it is put into
  HTML in `script.js` (Wikidata and OSM are publicly editable).
- Every fact shown must name its source.
- The visual design is a deliberate choice: warm paper background,
  Fraunces + Source Sans 3 + JetBrains Mono fonts, a patina-green and
  brass accent color. Ask the user before you change this direction.
- Before each work session, read this file and `PLAN.md` first.
- At the end of a work session, update this file: add what changed, and
  update "Known limitations". This file is how the next session knows the
  current state.
